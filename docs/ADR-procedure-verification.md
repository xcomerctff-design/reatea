# ADR-001: Проверка SQL-процедур прямо из редактора

## Контекст
Пользователь строит процедуру в визуальном редакторе (Rust/Tauri). Нужна кнопка
«Проверить»: валидация синтаксиса и семантики без выхода из IDE, ответ < 1 c.

## Рассматриваемые подходы

### A. Встроенный парсер на Rust (sqlparser / pg_query)
- (+) Нулевые зависимости, мгновенный запуск, нативно в Tauri.
- (-) Диалект ограничен; нет доступа к Java-AST и генератору — проверка расходится
  с тем, что реально генерируется. Дублирование логики в двух языках.

### B. JDBC-подключение к «проверочной» БД (development database round-trip)
- (+) Максимальная точность: реальная СУБД проверяет типы, существование таблиц.
- (-) Требует доступной БД у каждого пользователя; медленные проверки; утечка
  подключений; небезопасно выполнять тело процедуры на проде; не работает офлайн.

### C. Вызов Java-верификатора из Rust как внешнего процесса (JNI или subprocess)
Редактор сериализует AST в JSON → `java -cp sqlgen.jar org.sqlgen.verify.VerifyMain`
→ JSON-отчёт об ошибках обратно в редактор. Внутри — JSqlParser (офлайн-парсинг)
+ набор статических правил (проверка колонок по метаданным схемы, ключевые слова,
баланс BEGIN/END, параметры).
- (+) Единый источник истины: проверяется ровно тот AST, из которого генерируется код.
- (+) Работает офлайн, без БД. Портативно (просто JVM рядом с бандлом Tauri).
- (+) Изоляция: падение верификатора не роняет редактор (в отличие от in-process JNI).
- (-) Нужна JVM в дистрибутиве; старт процесса ~100–300 мс (компенсируется
  resident daemon-режимом: один долгоживущий процесс, stdin/stdout протокол).

### D. In-process JNI (libjvm.so загружается в процесс Tauri)
- (+) Быстрее subprocess (нет exec-оверхеда).
- (-) Хрупко: JVM нельзя выгрузить; OOM/крах JVM = крах всего приложения;
  усложнение сборки (jli, классpath, версии JDK). Эксперты отмечают плохое
  соотношение сложность/выигрыш для задачи «проверить текст».

### E. Сервис-обёртка (gRPC/HTTP sidecar)
- (+) Масштабируется на команду, единая точка обновлений правил.
- (-) Избыточно для desktop-приложения; лишний сетевой стек, порты, безопасность.

## Решение
**C (subprocess Java-верификатор) + опциональное усиление правилом EXPLAIN.**
Обоснование конструктивной критики экспертов:
- A отвергнут: рассинхрон проверки и генерации — главный риск продукта.
- B оставлен как *опция* (флаг `--dsn`): если пользователь указал тестовую БД,
  верификатор дополнительно выполняет `PREPARE`/`EXPLAIN` внутри
  `BEGIN ... ROLLBACK` — безопасно и точно.
- D отвергнут из-за риска стабильности; E — из-за избыточности.
Итоговая архитектура: Rust → JSON → Java VerifyMain (JSqlParser + схема-метаданные)
→ структурированный отчёт `{valid, errors[{line,col,message,severity}]}`.
